Sessions 13–14

From RAG to the Autonomous Enterprise

Nov 21, 2026Day 7Industry guest lecture

A guest lecture by Dr. Sumit, Senior Data Scientist and AGM at Reliance, on moving an enterprise from retrieval-augmented search to coordinated agent workflows, and the architecture, governance and sequencing decisions that journey demands. Implementation examples are kept general, since they describe his employer's internal systems.

Intended learning outcome

Place an organisation on a staged AI maturity path, specify the architectural layers each stage requires, and judge when agentic AI is the wrong instrument for the problem.

Executive Summary

  • Most organisations sit at stage two of four — retrieval-augmented question answering over connected data; the gap to agentic systems is architectural and organisational, not a matter of model choice
  • Multi-agent designs reduce hallucination by distributing responsibility, because loading one agent with many duties raises its error rate under load
  • Funding is approved one workflow at a time, each with its own cost projection and variance range, since full upfront estimation is impractical for work this novel

The four-stage maturity path

  1. 1Data-driven connectivity — every source identified, indexed, and its relationships to the others understood
  2. 2AI enablement — RAG and language models layered over that data, giving cited natural-language access
  3. 3Agentic systems — specialised agents that plan, call tools, and communicate with one another
  4. 4Connected autonomous enterprise — agents predict, extract, investigate and execute across workflows, reasoning and coordinating while humans stay in the loop

Dr. Sumit's definition of an autonomous enterprise is worth keeping precise: not a system that removes people, but one in which agents carry a workflow end to end and surface it for human decision at the points that matter.

The reference architecture

  • Data foundation — indexing across relational stores, document stores, vector databases and unstructured repositories, with a knowledge graph mapping entities, their attributes and their relationships beneath a semantic layer
  • Intelligence — language models with retrieval for natural-language interaction, predictive machine learning for forecasting and classification, and rule-based logic wherever the output must be deterministic
  • Agentic — specialised roles, planning capability, tool calling, and inter-agent communication, which is what separates an agent from a model behind a chat box
  • Trust and governance — authentication and role-based access, encryption, prompt-injection protection, citations attached to every output, audit trails, evaluation agents that validate other agents, and human review wherever money, critical operations or hallucination risk is in play

Two details stood out. Classical predictive models still outperform generative ones at forecasting and classification, so the generative layer is not a replacement for the statistical one. And the foundation is the expensive part: a data engineering team of fifteen to twenty people worked continuously for more than four months, prioritising the most recent five to ten years of history and deferring older records.

From chatbot to multi-agent system

  1. 1Chatbot — responds within a single turn, no memory of the task
  2. 2Assistant — retrieves and summarises against a known corpus
  3. 3Agent — holds a role, plans, and calls tools outside itself
  4. 4Multi-agent system — several agents with distinct responsibilities, coordinating and checking one another

Agent count follows no rule. It is set by workflow boundaries, by what testing shows, and by latency, since every additional agent adds overhead. The argument for splitting is reliability rather than elegance: a single agent asked to do six things hallucinates more than six agents asked to do one each.

An agentic operating layer

  • Reuse — a developer publishes an agent to a catalogue and other teams consume it through an API instead of rebuilding it
  • Concurrency — simultaneous demand on one agent is served by worker instances, virtual parallel copies of the same agent
  • Redundancy control — the platform flags overlapping agents, so duplicated capability surfaces before it proliferates

Use cases demonstrated

  • Departmental knowledge base — a unified index across HR records, dashboards, structured databases and unstructured leadership documents, air-gapped so nothing leaves the department, answering natural-language queries with citations; the same foundation now serves procurement, marketing and HR, which is the argument for treating it as infrastructure rather than a project
  • Tender and bid compliance — expression-of-interest generation, vendor document ingestion, automated compliance evaluation, digital signature and approval note; scanned documents pass through two-stage optical character recognition with the outputs compared character by character before anything downstream trusts them
  • Dynamic agent creation — the number of agents is decided at runtime from the number of tender criteria, each agent searching the vendor document for its own criterion, returning a pass or fail verdict with a cited summary, then terminating; the output is a compliance matrix of vendors against criteria, regenerated daily with confidence scores
  • Dashboards to decision intelligence — the queries underlying existing business-intelligence plots are extracted and fed to a monitoring layer that detects anomalies, simulates outcomes and delivers a root cause report to leadership within half an hour of a threshold breach
  • Exploration intelligence — a knowledge graph over sensor, well-log and geophysics data, layered as physics rules, then certainty rules, then predictive models, then a reasoning layer, then specialist agents, with domain experts reviewing every output before an operational decision
  • Recruitment — job description drafting through screening, AI-conducted interviews and evaluation summaries, with the final hiring decision explicitly retained by the business

Integrating systems that cannot be replaced

An ERP that has run for decades is not replaced to accommodate an agent. The practical answer is a buffer layer that translates agent requests into the legacy system's own API calls, with one dedicated agent owning all traffic across that boundary.

  • Track one — the API bridge, which delivers integration immediately and accepts a latency cost
  • Track two — gradual migration of the same data into the AI-native store, enriching it until the bridge can be retired

Running both at once is the point. The bridge buys time; the migration removes the dependency that the bridge creates.

Hosting the model: build versus buy

FactorManaged APISelf-hosted open source
Speed to deployFast — no infrastructure to stand upSlow — requires DevOps and LLMOps capability in house
Cost structureRecurring token cost, scaling with usageHigh upfront, lower marginal cost per call
Data controlLower — requests leave the organisationFull — data stays on the organisation's own infrastructure
CustomisationManaged updates, limited control of the model itselfFull control of model, serving and fine-tuning
Best suited toSmaller organisations and non-sensitive dataLarge organisations, sensitive or financial data

The sovereignty variant sits between the two: proprietary models running on instances the organisation hosts in its own country, so the model is bought but the data never leaves. Models with no in-country hosting raise data-residency questions that a procurement conversation has to answer before a technical one. For learning rather than production, a local runtime on a well-specified laptop is enough to build and test agents without paid APIs — capable, though below cloud-scale performance.

This is the complementary assets argument from Sessions 9–10 appearing in an infrastructure decision. An organisation that already owns data centres can hold the asset; one that does not, rents it.

Sequencing and roadmap

PhaseDurationFocus
Foundation0–6 monthsData connectivity, indexing, basic retrieval
Production and orchestration6–12 monthsAgentic workflows, integration, trust layer
Connected autonomy12–24 monthsCross-workflow orchestration, enterprise-wide AI
Full autonomous enterprise24–48+ monthsUnified organisational intelligence

These durations describe a very large organisation. A smaller one with fewer departments may reach the first two stages inside six to twelve months, but it hits a different constraint: a small team becomes a bottleneck in data engineering, data science and operations simultaneously. Deployment is therefore incremental by design — one workflow at a time, which controls cost, builds trust, and makes return measurable before the next commitment.

Leadership and governance principles

  • Five ingredients — a low-cost first workflow, data readiness, architecturally sound integration, a trust layer, and an adoption and feedback loop
  • Portfolio — systems must be repeatable and reusable across cases; disconnected one-off builds undermine the next one
  • Platform — shared model, data and evaluation platforms lower cost and keep adoption consistent
  • Governance — balance autonomy against accountability, avoiding both over-restriction and unchecked autonomy (risk management frameworks and risk-tier regulation are the external reference points here)
  • Direction of decisions — not orders passed down: business units bring goals, technical teams assess feasibility and propose an approach, and the two meet on resources and timeline
  • Capability building — leaders have to make the productivity case explicitly, because adoption stalls when people read automation as redundancy

When not to use agentic AI

  • Deterministic output — if the answer is fully determined by the inputs, use a rule-based system
  • Zero hallucination tolerance — use strict rules with mandatory human review instead
  • Immature processes — fix the process first; an agent does not compensate for structural dysfunction, it inherits it
  • Undefined scope — undefined scope produces unbounded feature creep and a system nobody can test

Measuring value

  • Productivity — throughput and task completion speed
  • Financial — cost reduction or monetary advantage created
  • Quality — performance against the system being replaced
  • Risk — data exposure, security incidents, hallucination rate
  • Adoption — actual end-user utilisation, which he called the most telling indicator of real value

Questions I raised

  • Connecting existing dashboards to an intelligence layer — extract the queries behind each plot, feed them into the system, set a monitoring interval, and let anomaly detection trigger an automatically generated root cause report to leadership
  • Approving and funding AI work before it is built — present one workflow at a time with projected cost, a variance range and trade-off scenarios, rather than attempting a full upfront estimate that the novelty of the work cannot support

Proposed Year-2 electives

Part of the session turned to curriculum for the Digital Transformation stream, with three areas identified: AI and data governance, covering sovereignty, access control, audit trails and model operations; agentic system deployment, covering architecture, deployment patterns and observability rather than coding; and multi-agent systems, covering inter-agent communication, tool calling and agent reuse. The suggested format was twenty sessions of ninety minutes, split evenly between theory and hands-on architecture work, with curated material in place of a textbook.

Open questions

  • Current token pricing is widely understood to be subsidised. How should a multi-year agentic programme be costed when the unit price of its core input is unsettled?
  • Which of the three proposed electives will carry this material, and will they be available to this batch?
  • Once the session slides are circulated, which of the use cases warrant a deeper follow-up for an operations context?

Leadership Reflection

What this session means for manufacturing leaders:

The maturity model is a diagnostic, and an uncomfortable one. A plant that cannot say where its data lives, or how its quality records relate to its machine logs, is at stage one regardless of which tools it has licensed. Connectivity before intelligence, intelligence before agents — in that order, and the order is not negotiable.

The compliance pattern transfers almost directly. Supplier qualification, incoming inspection documentation and certificate verification share the shape of the tender use case: high document volume, criteria that are already written down, and a verdict that must be auditable. Spawning one checker per criterion, each returning a cited pass or fail, is a design a quality function can recognise and defend.

Two cautions are worth carrying into any such proposal. A broken process does not improve by having an agent placed on top of it, so process maturity is a precondition rather than an outcome. And since adoption is the metric that exposes everything else, the honest question to ask of a pilot is not whether it worked but whether anyone kept using it.
